# OMIYAcappella

The website for **OMIYAcappella**, an a cappella community in Omiya, Saitama, Japan.

**Live: <https://omiyacappella.com>** · Japanese at the root, English under `/en/`
· [@OMIYAacappella](https://x.com/OMIYAacappella)

Plain HTML, CSS and JavaScript with no browser-side dependencies, generated by a
Python script and served from Cloudflare Workers. Total running cost: the domain.

---

## Why this exists

I sing with an a cappella community in Saitama. It started in 2022 and has grown
to 37 members, and its organiser had been telling me the same thing for a while:
recruiting is hard, and he did not know how to fix it.

The numbers behind that worry are in this repository, because the site's project
timeline is built from the group's actual history. In four years and four months
the group has run **40 activities — 23 of them calls to form a band**, roughly one
every two to three months. Broken down by year: 10, 11, 4, 9, and 6 so far in 2026.
The community works. It just did not grow.

The reason was narrower than it looked. **The only way to find this group was to
already follow one X account.** Someone in Saitama who wanted to sing had no path
to us — not a search result, not a directory listing, nothing that answers "is
there a cappella near me?" We were invisible to precisely the people we wanted.

So the problem was not recruitment copy. It was reach and evidence: be findable
when someone searches, and once found, show enough that a stranger can decide
whether to get in touch.

This site is the answer to that, and it is deliberately measurable. It carries

- **video and audio of the group actually singing** — performances and project-band
  recordings, playable on the page, so the standard is visible rather than claimed;
- **every project the group has run since 2022**, so a visitor can see the real
  cadence and what a "one-day band" actually involves;
- **a contact form that reaches the organiser directly**, replacing "send a DM to
  an account you have to find first".

It went live on 25 August 2026. Analytics and form submissions are now being
tracked to find out whether any of this works — that verification is in progress,
and the answer is not in yet. What is built is the instrumentation to get one.

### What I would look at next

The honest version: the site is new, the sample is small, and I would rather
report a real number later than a promising one now. The measurements that will
decide whether this succeeded:

1. **Impressions and clicks in Search Console** for 「埼玉 社会人 アカペラサークル」
   (adult a cappella circle, Saitama) — does anyone find us by searching?
2. **Contact form submissions** — does being findable convert into people writing in?
3. **Contact page views vs. submissions** — the join form asks for seven extra
   fields. If people arrive and leave, the form is too heavy and should be cut back.

## Engineering notes

The parts worth reading, in the order I would want to read them.

### One source, two languages

Root `*.html` files are **generated**; editing them is lost on the next run.
`scripts/assemble.py` composes each page from a shared shell plus sections in
`parts/`, and writes Japanese to the root and English to `en/`.

```bash
python3 scripts/assemble.py
```

The shell — header, navigation, footer, page hero, breadcrumbs, titles,
descriptions, structured data — is defined once per locale in the script, so the
two languages cannot drift apart structurally. **The build fails if a translation
is missing**, rather than quietly publishing a Japanese page under `/en/`.

Every absolute url the site emits — canonical, `hreflang`, `og:url`, the sitemap,
`robots.txt` — is derived from a single `SITE_URL` constant. Moving hosts is a
one-line change, and there is nowhere for a stale domain to hide.

### Video is self-hosted, because X will not allow otherwise

The gallery originally embedded the group's X posts. Two things killed that:

1. **`video.twimg.com` blocks hotlinking by `Referer`.** No referer returns 200;
   a referer from another site returns 403. `<video src="https://video.twimg.com/…">`
   simply does not play.
2. **X's embed widget is unreliable.** It has periods of not responding, during
   which the section renders as a blank rectangle.

So the 14 clips (89 MB, largest 15.6 MB) are served from this site and played in a
native `<video>` / `<audio>` element. If playback fails, the lightbox falls back to
a link to the original post. Six of the clips were screen recordings of voice memos,
which look wrong as thumbnails, so those render as waveform cards drawn from a
brand-coloured SVG instead.

### Extensionless urls, because the platform insists

Cloudflare's asset server drops `.html` and 307s anything still carrying it. The
first deploy shipped with `.html` everywhere, which meant **every url in the sitemap
was a redirect, and every canonical tag named a detour rather than a destination —
including the one on the page serving it.**

Rather than fight the default, the generator now emits the extensionless form
everywhere, while still writing `about.html` to disk because that is the file the
asset server maps `/about` to. `scripts/dev-server.py` was taught the same mapping,
so local preview and production agree about what a link means.

### The contact form never sees the address

The destination is not in the page, the JavaScript, or the repository. The form
posts to `/api/contact`, a Worker that validates the submission and forwards it,
with the address held in a Cloudflare secret.

Choosing `参加を希望する` ("I want to join") reveals seven more fields — gender, age,
prefecture, circle, years singing, parts they can cover, and an optional social
handle. Switching away hides them **and clears them**, so an unrelated enquiry never
carries personal data it has no reason to.

### Two bugs worth writing down

**Changing a secret does nothing until the version is deployed.** This Worker uses
versioned deploys. Adding a secret in the dashboard creates a new version and
leaves the running one untouched — the form kept returning 503 with the secret
plainly visible in the UI. `wrangler secret put` refuses outright for the same
reason. The fix is to promote the version, from Deployments or via
`npx wrangler versions deploy`.

**FormSubmit answers 429 to Cloudflare's IPs.** After the secret was live, every
submission failed. Eight retries over five minutes all returned 429, which looked
like rate limiting. Sending the identical request to the identical endpoint from a
home connection at the same moment returned 200 — so the limit was the source
address, not the volume. Activating the form (the other candidate explanation)
changed nothing: the same comparison afterwards still gave 429 from Cloudflare and
200 from a home line.

Two real defects surfaced while isolating that:

- **No `Origin` header.** FormSubmit reads a request without one as a page opened
  from the filesystem and answers with advice instead of sending. A browser sets it;
  a Worker forwarding server-side has to set it itself.
- **A refusal arrives as HTTP 200** with `success:"false"` in the body. The Worker
  checked only the status code, so it had been **reporting deliveries that never
  happened**. It now surfaces the reason as a 502.

The fix was to stop relaying and start sending. Cloudflare's own Email Sending
binding was the obvious candidate — no API key, no external account — but it
requires the Workers Paid plan, so mail goes through **Resend** instead. It
authenticates by API key rather than by source address, which is the property
FormSubmit lacked, and it sends from the site's own domain rather than a relay's,
which also helps the mail survive spam filtering. Recipients and the key live in
secrets, since this repository is public.

### The X section updates itself

`.github/workflows/x-latest.yml` runs daily at 06:00 JST and commits only when
something changed:

```
Playwright opens x.com/OMIYAacappella
  → collect status ids, excluding the pinned post
  → fetch each through X's syndication endpoint (no API key)
  → keep the newest three
  → save images, video and thumbnails to assets/data/x-media/ and prune the rest
  → write assets/data/x-latest.json
```

It costs nothing (1–2 minutes per run on the Actions free tier). **A failure changes
nothing** — the previous JSON stays, and if that is missing too, `main.js` falls back
to three posts written into the source. The section cannot end up empty.

## SEO

The two targets are **「埼玉 社会人 アカペラサークル」** (adult a cappella circle,
Saitama) and **「埼玉 アカペラ サークル」**. 「埼玉 アカペラ」 is not worth chasing —
the results mix vocal schools, concert listings and the prefectural anthem, so the
intent is too scattered to convert.

What made these winnable is that the top results are **aggregators, not the sites of
individual groups**. The slot for "the official site of an adult a cappella group in
Saitama" was empty.

Before: no page contained the word 埼玉, and no title contained 社会人 or サークル —
the site could not have ranked for words it never used. Since:

- Titles and descriptions carry the region. Every title used to end in a second copy
  of the site's own name; that half is now what a searcher actually types.
- The hero opens by addressing the search directly — "looking for an adult a cappella
  circle around Omiya in Saitama?" — and the next sentence corrects it, because the
  group is deliberately not a circle. **Meeting people with their own word beats being
  unfindable and precise.**
- `robots.txt`, `sitemap.xml` (12 urls, generated), canonical, `hreflang` (ja / en /
  x-default), and schema.org `Organization` naming Saitama and Omiya as the area served.

Off-site: registered with Google Search Console (sitemap accepted, 12 pages found),
the site url added to the X profile, and a listing request sent to pellaten, an
a cappella directory that currently outranks every individual group. Directory
backlinks matter more here than anything on the page, because backlinks are exactly
why those aggregators hold the top slots.

### Analytics

**Cloudflare Web Analytics, with no setup.** Because the domain sits on Cloudflare,
the beacon is injected at the edge for browser requests (it does not appear in
`curl` output, which is why it is worth saying). No cookies, no local storage, and
therefore **no consent banner** — switching to Google Analytics would require one.

`ANALYTICS_TOKEN` in `scripts/assemble.py` exists for a future move off Cloudflare
and **must stay empty**, or visits get counted twice.

## Stack

| | |
| --- | --- |
| Frontend | HTML, CSS, vanilla JS — no framework, no build step, no runtime dependency |
| Generation | Python 3 (`scripts/assemble.py`), no template engine |
| Hosting | Cloudflare Workers with static assets |
| Backend | One Worker route (`/api/contact`) |
| Mail | Resend API, called from the Worker |
| Automation | GitHub Actions + Playwright, daily |
| Analytics | Cloudflare Web Analytics |
| CI/CD | Cloudflare Workers Builds — push to `main` deploys |

No framework was a deliberate choice, not an omission. The site is twelve mostly
static pages that need to load fast on a phone on a train platform, be editable by
someone who is not me, and still be running unattended in three years. A build
toolchain would have added upgrade work without buying anything the pages need.

## Repository layout

```
.
├── index.html about.html gallery.html projects.html contact.html rules.html
├── en/                 # the same six pages in English  ── all generated
├── robots.txt sitemap.xml                               ── generated
├── parts/              # page content — edit here
│   └── en/             # its translation, one file per Japanese file
├── scripts/
│   ├── assemble.py         # parts/ + shell → every page
│   ├── build.sh            # assemble dist/ for publication
│   ├── dev-server.py       # local preview, no-store, extensionless urls
│   ├── fetch-x-latest.mjs  # daily X fetch (GitHub Actions)
│   └── _headers            # cache and security headers
├── worker/index.js     # asset serving + /api/contact
├── wrangler.toml       # Cloudflare deploy config
├── server/             # LINE webhook → project feed (built, not deployed)
└── assets/             # css, js, img, video (14 files, 89 MB), data
```

**Edit `parts/`, not the root HTML.** Header, navigation, titles, descriptions and
menu copy live in `scripts/assemble.py`.

## Running it

```bash
python3 scripts/dev-server.py 4321      # then http://localhost:4321
```

A dedicated server rather than `python3 -m http.server` for two reasons: everything
is returned `no-store`, because otherwise the browser holds on to old CSS and JS
across reloads and you debug a file you already fixed; and it resolves `/about` from
`about.html` the way Cloudflare does.

To exercise the production shape, including `/api/contact`:

```bash
bash scripts/build.sh
npx wrangler dev --port 8788 --local     # secrets go in .dev.vars (gitignored)
```

`scripts/build.sh` is not optional. Publishing the repository root would serve
`README.md`, `server/` and `scripts/` at their own urls; the script copies only the
generated pages, `assets/`, `robots.txt`, `sitemap.xml` and `_headers` into `dist/`.

## Deployment

Pushing to `main` triggers Cloudflare Workers Builds, which runs
`bash scripts/build.sh` then `npx wrangler deploy`.

The domain is registered through Cloudflare Registrar and bound to the Worker as a
custom domain on the apex only. Everything else is funnelled to it, so the content
exists at exactly one url: `www` redirects 301 via a rule, `http` upgrades via
Always Use HTTPS, and the `workers.dev` subdomain is switched off.

## Known issues

1. **No privacy policy.** The join form collects gender, age and location. One is owed.
2. **LCP p99 is around 11 s** on gallery pages, from the video weight. Re-encoding at
   640×360 would cut the files to roughly a third.
3. **The LINE integration in `server/` is built but shelved.** It is tested and
   unwired; if revived, `ALLOWED_ORIGIN` still points at a retired GitHub Pages url.
4. **One date in the project timeline is an estimate** — a March 2026 entry whose
   posting date was not visible in the source screenshot, inferred from the entries
   either side of it.

## Privacy in the project timeline

The timeline is reconstructed from a private LINE group. **Posters' names and sheet
music urls are never shown**, and social arrangements, membership changes and
anything identifying who wrote what are excluded. What remains is calls for bands,
event appearances and organisers' announcements.
